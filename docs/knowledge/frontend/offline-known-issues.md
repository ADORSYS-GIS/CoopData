## 3. What Each Fix Changed

### A — Submission page crashes offline

- **Problem:** with nothing saved for some data, `useOfflineQuery` invented a placeholder (`{}` or `[]`) based on words in the cache label. Pages trusted it and crashed (`submission.id.slice`, `j.filter is not a function`).
- **Fix:** no invented data. Without a saved copy, the caller's explicit `fallbackData` is used, or the query errors (`OfflineDataUnavailableError` offline) and the page shows _"This information isn't available offline yet…"_.
- **Files:** `hooks/shared/useOfflineQuery.ts`, i18n `offline.dataUnavailable`.

### H — Placeholder data stuck after reconnecting

- **Problem:** placeholders were stored as fresh data for 5 minutes. And when the app _started_ offline, the data library never noticed the connection coming back.
- **Fix:** data shown from the device is marked old, so it reloads on reconnect. TanStack's `onlineManager` is seeded with `navigator.onLine` at startup.
- **Files:** `useOfflineQuery.ts`, `router.tsx`.

### G — Pre-downloaded data never found

- **Problem:** the seeder and the hooks typed labels by hand and drifted apart: apex members (`cooperative-members-{id}` vs `cooperative-{id}-members`), ministry stats, ministry cooperatives list. Translated data was only seeded for 3 of the 4 languages.
- **Fix:** one shared module (`offlineCacheKeys.ts`) builds every seeded location for both sides. The seeder covers every language in `SUPPORTED_LANGUAGES`.
- **Files:** `services/shared/offlineCacheKeys.ts` (new), `offlineSeeder.ts`, 19 hook files, `i18n/index.ts`.

### B — Decisions clickable offline (and apex offline drafts)

- **Problem:** submit, approve/return/reject, AI validation and narrative generation were queued offline and applied later. Delegate, reclaim, claim edit, deletes and uploads failed with a confusing network error. Apexes couldn't create drafts offline at all.
- **Fix:** `assertOnline()` is the first line of every online-only action (so nothing changes on the device), and buttons are disabled offline with a hint. Apex creation works offline like the cooperative's: the backend accepts a client-generated `id`, and a shared helper saves the local draft placeholder.
- **Files:** `services/shared/networkGuard.ts` (new), `localDraftSubmission.ts` (new), `syncQueueService.ts`, 20 hooks, submission pages; backend `CreateApexSubmissionRequest.id`.
- **Deploy note:** deploy the backend with or before this frontend.

### C — Outbox not sent after starting offline

- **Problem:** starting offline skipped the Keycloak start-up, and nothing completed it later, so offline mode stayed on until a reload.
- **Fix:** `restoreOnlineSession()` runs when the connection returns: it completes the Keycloak start-up with the saved login, leaves offline mode, sends the outbox and reloads data. Limitation: if Keycloak was unreachable at startup while the browser was online, a reload is still needed.
- **Files:** `authService.ts`, `AuthContext.tsx`, `__root.tsx`. Also fixed a test isolation bug in `useNetworkStatus.test.tsx`.

### C-2 — Stuck offline when Keycloak answers late (found by the PR #217 review)

- **Problem:** the network is often reported up a moment before it works. The single restore attempt then failed, and since keycloak-js can only initialise once per page, the app stayed offline (banner, disabled actions, unsent outbox) until a reload.
- **Fix:** `restoreOnlineSession()` now first checks that Keycloak answers, and reports why it couldn't restore (`unreachable`, `ended`, `reload`). `keepRestoringSession()` retries while unreachable (10 s → 5 min). A refused saved login logs the user out (work kept), and a spent start-up shows a **Reload** prompt.
- **Files:** `authService.ts`, `sessionRestore.ts` (new), `AuthContext.tsx`, i18n `offline.reconnectNeedsReload`, `offline.reload`.

### D — Duplicate saves

- **Problem:** the first, online attempt of a save went out without its `X-Correlation-Id`. If the reply was lost, the retry used an id the server had never seen.
- **Fix:** the save's id is attached to its first request too (openapi-client middleware and a `fetch` wrapper). The backend's idempotency check then answers "already done" to the retry.
- **Files:** `services/shared/correlation.ts` (new), `syncQueueService.ts`, `openapi-client/index.ts`, `main.tsx`.

### E — "Already exists" counted as saved

- **Problem:** the outbox marked any "already exists"/"duplicate" answer as done, including real conflicts, so offline work could be lost silently.
- **Fix:** a 409/422 is `failed`, with the server's message and status.
- **Files:** `syncQueueService.ts`, `offlineDb.ts` (`lastStatus`).

### F — Failed changes invisible

- **Problem:** failures were never shown, 404s were retried, and all retries ran within about 12 seconds.
- **Fix:** a **"Not saved: N"** badge and panel (plain-language description, reason, Retry/Dismiss/Retry all). Refusals (400/403/404/409/410/422) fail at once; temporary errors back off 10s → 30 minutes. A refused online save isn't retried in the background; a network drop mid-save is queued like an offline save. The stuck-item rescue uses `syncStartedAt` (old #14).
- **Files:** `syncQueueService.ts`, `describeSyncItem.ts`, `useFailedSyncItems.ts`, `SyncProblemsDialog.tsx`, `OfflineStatusBanner.tsx`, i18n `sync.*`.

### I — Page snapshot fails to save

- **Problem:** the snapshot included queries still loading. Their in-flight Promise can't be stored in IndexedDB (`DataCloneError`): 18 failures in a short browse.
- **Fix:** only finished, successful queries are saved (`defaultShouldDehydrateQuery`).
- **Files:** `routes/__root.tsx`.

### #10 — Shared-device data leak

- **Problem:** lookups fell back to _any_ user's saved copy of a label, so a failed request could show one organisation's data to another.
- **Fix:** that fallback is limited to data identical for everyone (organisation labels, active templates, indicator catalogs).
- **Files:** `services/shared/offlineCache.ts`.

### D-3 — Offline invitations

- **Change:** offline invite and resend say _"saved on this device, sent when you're back online"_.
- **Files:** `InvitationList.tsx`, `ApexUsersPage.tsx`, `CooperativeMembersPage.tsx`, i18n `offline.inviteQueued*`.

### D-5 — Logout keeps work (and the logout race)

- **Change:** drafts are owned per user (DB schema v4) and, with the outbox, survive logout. A manual logout warns when offline or with unsent changes. Offline, logout opens the start page.
- **Bug found and fixed:** `keycloak.logout()` returned while navigating; the app then jumped to `/login`, whose sign-in could cancel the logout and sign the user straight back in. `logout()` now never resolves once it starts leaving, and also removes the saved profile copy.
- **Files:** `manualEntryDraftService.ts`, `offlineDb.ts`, `authService.ts`, `AuthContext.tsx`, `LogoutConfirmDialog.tsx`, `app-shell.tsx`.

### J — Saved login outlives Keycloak's deadline

- **Problem:** Keycloak ends the offline session **30 days after the password sign-in** (`offlineSessionMaxLifespanEnabled`), and every refreshed offline token keeps that same `exp` (checked on the local Keycloak). The app instead counted 30 days from the **last refresh**, so a user signed in on day 0 and offline from day 25 could keep working offline until day 55, then hit an unexpected sign-in. It also checked only at startup.
- **Change:** the deadline is the offline token's `exp` (`refreshTokenExpiry`), with the old 30-days-from-refresh rule only as a fallback when a token has no `exp`. A new `useSessionDeadline` hook checks it every minute: when it passes, the app logs out (drafts and outbox kept); in the last 3 days the status pill shows "Sign-in ends in N days". The offline "no session" screen now says "Please connect to the internet to sign in" (it no longer says "for the first time").
- **Files:** `authService.ts` (`offlineSessionExpiry`, `getOfflineSessionExpiry`), `useSessionDeadline.ts`, `AuthContext.tsx`, `OfflineStatusBanner.tsx`, i18n `sessionDeadline.*`, `offline.noSessionDesc`.

## 5. How the Issues Were Reproduced (2026-10-10)

**Setup:** the `frontend-pwa` container on `http://localhost:5174` (production build with service worker), driven by **Playwright + Chromium** with the local test accounts. Offline was simulated with Playwright's `context.setOffline(true)`.

The built-in browser of the Claude desktop app **can't register service workers**, so it isn't usable for offline testing. Use a real Chrome/Chromium or Playwright.

**Safety:** no real data was changed. Outbox items were written in the exact shape `enqueue()` produces, pointing at endpoints the server rejects. The one test record created (a custom KPI) was deleted afterwards.
