# Testing Offline Mode Locally

> **TL;DR:** Offline mode does **not** work on `http://localhost:5173` (the Vite dev server). Test it on **`http://localhost:5174`**, which `docker compose up` now serves as a production build with the service worker enabled.

---

## 1. The Symptom

You open the app on `localhost:5173`, set DevTools → Network → **Offline**, reload, and get the Chrome dinosaur page (`ERR_INTERNET_DISCONNECTED`) instead of the app.

In the Network tab, the `dashboard` document request shows `(failed)` with `0.0 kB`. If a service worker were active, that row would show `(ServiceWorker)` instead.

**Nothing in the offline code is broken.** The app is being tested in a mode where offline cannot work.

---

## 2. Why It Happens

### 2.1 Offline loading needs a service worker

To open the app with no network, the browser needs a copy of the app already saved locally. The **service worker** (`sw.js`, generated by `vite-plugin-pwa`) does that saving:

- On the first online visit, it precaches every app file (JS, CSS, HTML, icons, fonts).
- On later visits, if the network is down, it serves those saved files.

The service worker only saves the **app shell**. Data comes from IndexedDB (`offlineDb`, see [`offline-first-architecture.md`](../../features/offline-first-architecture.md)).

### 2.2 The service worker is disabled in dev mode, on purpose

```ts
// frontend/vite.config.ts
VitePWA({
  // ...
  devOptions: {
    enabled: false,
  },
});
```

There are two reasons:

1. **There is nothing to precache in dev mode.** The list of files to save is written into `sw.js` by `npm run build`, from the files in `dist/`. The dev server never builds. It serves hundreds of unbundled source modules on the fly (`/src/hooks/useMembers.ts?t=…`), and their URLs change on every edit. Even with the service worker enabled, it would only cache the `index.html` shell, and an offline reload would still fail.
2. **It would break hot reload.** A service worker answers requests from its cache instead of the server. During development, that means you edit a file and the browser keeps showing the old version. Service workers also persist after the tab is closed, which leads to long "why isn't my fix showing?" sessions.

`vite-plugin-pwa` itself ships with dev mode off by default for these reasons.

### 2.3 `docker compose up` only started the dev server

The repo has two compose files that Docker merges automatically when you run `docker compose up` **without `-f`**:

| File                          | `frontend` service                                                                |
| ----------------------------- | --------------------------------------------------------------------------------- |
| `docker-compose.yml`          | Production build: `frontend/Dockerfile` → `npm run build` → nginx, port `5174:80` |
| `docker-compose.override.yml` | **Replaces it** with the Vite dev server: `Dockerfile.dev`, port `5173`           |

The override wins, so locally only the dev server ran. There was no way to reach a built, offline-capable frontend.

There was also a side issue. Compose **merges** `ports` lists instead of replacing them, so the dev container also got the base file's `5174:80` mapping. Nothing listened on port 80 inside the dev container, so port 5174 was taken but did nothing.

---

## 3. The Fix

Both changes are in `docker-compose.override.yml`:

```yaml
frontend:
  # ...dev server, unchanged...
  ports: !override # use only this list; don't merge the base file's 5174:80
    - "5173:5173"

frontend-pwa:
  build:
    context: ./frontend
    dockerfile: Dockerfile # the same production recipe CI uses
    args:
      VITE_API_BASE_URL: "" # relative /api → nginx proxies to backend:3000
      VITE_KEYCLOAK_URL: http://localhost:8180
      VITE_KEYCLOAK_REALM: coop-data
      VITE_KEYCLOAK_CLIENT_ID: coopdata-frontend
  container_name: coopdata-frontend-pwa
  ports:
    - "5174:80"
  depends_on:
    - backend
```

`docker compose up` now starts both frontends:

| URL                     | What runs                 | Service worker | Works offline | Hot reload | Use it for            |
| ----------------------- | ------------------------- | -------------- | ------------- | ---------- | --------------------- |
| `http://localhost:5173` | Vite dev server           | ❌             | ❌            | ✅         | Day-to-day coding     |
| `http://localhost:5174` | Production build on nginx | ✅             | ✅            | ❌         | Testing offline / PWA |

**Why port 5174:** Keycloak's `coopdata-frontend` client already lists `http://localhost:5174/*` as a valid redirect URI (`keycloak/realm-coopdata.json`), so login works without realm changes.

**Why `VITE_KEYCLOAK_URL` is passed explicitly:** with an empty value, the production bundle falls back to `window.location.origin + "/auth"`. The local nginx (`frontend/nginx.conf`) doesn't proxy `/auth`, so login would fail.

## 4. How to Test Offline

1. Start the stack as usual: `docker compose up -d`. The first run builds the `frontend-pwa` image, which takes a few minutes.
2. Open **`http://localhost:5174`** in a normal (non-incognito) window, with DevTools → Network set to **No throttling**.
3. Log in and open a few pages. The offline seeder also pre-caches role data right after login.
4. Check DevTools → **Application** → **Service workers**: `sw.js` should be **activated and is running**.
5. Check **Application** → **IndexedDB** → `CoopDataOfflineDB`: the tables should contain rows.
6. Switch Network to **Offline** and reload. The app loads, the offline banner shows, and cached data is displayed.
7. While offline, save something allowed offline (for example, add a member to a draft you hold). It appears in IndexedDB → `syncQueue` with `status: "pending"`. Actions that need the server (submit, approve, delete…) are disabled offline.
8. Switch back to **No throttling**. Within a few seconds the item changes to `status: "done"`. If the server refuses it, a red **"Not saved"** badge appears on the network pill.

### Automated offline tests (Playwright)

18 end-to-end checks run against the PWA build on `:5174`:

| File                                         | Covers                                                                                                                                                                 |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `frontend/e2e/specs/offline.spec.ts`         | App opens offline; no crash on uncached submissions (A); pre-downloaded data found offline (G); pages refresh on reconnect (H); page snapshot saves without errors (I) |
| `frontend/e2e/specs/offline-actions.spec.ts` | Online-only actions disabled offline and drafts allowed (B, apex drafts); honest offline invitation message (D-3)                                                      |
| `frontend/e2e/specs/offline-sync.spec.ts`    | Outbox sends after an offline start (C); same correlation id on every attempt (D); "already exists" reported as failed (E); "Not saved" panel (F)                      |
| `frontend/e2e/specs/offline-logout.spec.ts`  | Logout warns first offline; drafts and unsent changes survive logout (D-5)                                                                                             |

```bash
cd frontend && npm run test:e2e:offline
```

Requirements:

- the stack is running (`docker compose up -d`), with `frontend-pwa` built from your current code
- the `E2E_*` accounts in `frontend/.env`. The apex account needs a cooperative with members; the ministry account needs at least one submission. Tests skip with a reason when data is missing.

Runs with one worker (parallel logins overload the local backend), takes about 1.5 minutes, and is skipped in CI and when `:5174` isn't reachable. Use `npm run test:e2e:offline:headed` to watch it. No test changes server data: outbox items point at a non-existent endpoint, and anything queued for real is removed before reconnecting.

To check the fixes **by hand**, follow [`offline-review-guide.md`](offline-review-guide.md).

### After changing frontend code

Port 5174 is a build, so it does not pick up edits automatically. Rebuild it:

```bash
docker compose up -d --build frontend-pwa
```

Then reload once while **online**, so the service worker installs the new version (`registerType: "autoUpdate"`).

### Gotchas

- **The first visit must be online.** The service worker can only save the app during an online visit.
- **Incognito wipes everything when the window closes**, including the service worker and IndexedDB. Use a normal window for tests that span a browser restart.
- **Service workers require HTTPS or `localhost`.** Opening the app via a LAN IP over plain `http://` will not register one.
- **Stale version after a rebuild?** DevTools → Application → Service workers → **Unregister**, or Application → Storage → **Clear site data**, then reload online.

## 5. Impact on Production

**None.** Production is started by `start-prod.sh`, which always passes `-f docker-compose.ghcr.yaml`. When `-f` is given, Docker ignores `docker-compose.override.yml`, and that's the only file this fix changed.

| File                          | Changed | Used by                                |
| ----------------------------- | ------- | -------------------------------------- |
| `docker-compose.override.yml` | ✅      | Local `docker compose up` only         |
| `docker-compose.yml`          | ❌      | Local                                  |
| `docker-compose.ghcr.yaml`    | ❌      | Production (`start-prod.sh`)           |
| `frontend/Dockerfile`         | ❌      | CI builds the production image from it |
| `frontend/vite.config.ts`     | ❌      | Both                                   |

### How production serves the offline-capable app (unchanged)

```
push to repo
  → GitHub Actions (.github/workflows/docker.yml)
      builds frontend/Dockerfile: npm run build → dist/ + sw.js → nginx image
  → pushed to ghcr.io/adorsys-gis/coopdata-frontend
  → start-prod.sh pulls it and runs docker-compose.ghcr.yaml
  → browser → host nginx (HTTPS, Let's Encrypt) → nginx-proxy :5174 → frontend container
```

Production always runs the built app over HTTPS, so the service worker has always been available there. The fix only gives developers a local equivalent.
